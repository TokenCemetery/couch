# Couch

<img src="docs/logo.svg" alt="Couch logo" width="132">

A Go backend compatible with Emby Web: local user accounts, sessions, settings, movies, a basic TV series hierarchy, music, home videos and photos, direct HTTP delivery and saved playback position. The media library is read-only.

The reference is Emby Web **4.10.0.40**. The original API modules and the browser scenario "search → item page → play → seek → stop → restart → resume" have been verified; the limits of that verification are described in [VALIDATION.md](docs/VALIDATION.md), the verified combinations of formats and delivery methods in [COMPATIBILITY.md](docs/COMPATIBILITY.md), and what is supported, partial or missing in [FEATURES.md](docs/FEATURES.md). This is a prototype, not a replacement for a production Emby. Resource use is compared with Emby in [BASELINE.md](docs/BASELINE.md): Couch uses less at idle, in the API, Direct Stream and remux; transcoding uses about the same CPU but starts and seeks slower.

## Running

Requires Go 1.26+ and Linux/macOS.

```sh
go -C src build -o ../bin/couch ./cmd/couch
```

Create the first local user; it is the server's administrator, who adds other users from Emby Web. The password is passed via stdin, at least 12 bytes. Example for the current zsh shell; the input is hidden and does not end up in the command history:

```zsh
read -rs 'couch_password?New Couch user password: '
printf '\n'
printf '%s\n' "$couch_password" | ./bin/couch -init -username viewer
unset couch_password
```

Start the server with a full local copy of Emby Web:

```sh
./bin/couch -web-dir ../emby-webui
```

Address: <http://127.0.0.1:8097/>. The user `viewer` and the password set above belong to Couch; Emby accounts are not imported.

`-web-dir` points to the folder containing `index.html`, not its parent. Couch reads the UI unmodified; it adds `data-appversion="4.10.0.40"` to the served source `<html>`. This is a loader setting, not automatic version detection for an arbitrary UI. The provided API modules match the 4.10.0.40 reference. The provided copy was missing four files the client loads at startup: `modules/apphost.js`, `modules/input/keyboard.js`, `modules/virtual-scroller/virtual-scroller.js` and `.css`; on 2026-10-06 they were copied from the reference Emby 4.10.0.40, and Emby Web starts with `-web-dir` (#19). Of the remaining 307 files the client loads on the home screen, in libraries, search, series and movie pages, all user settings and the playback screen, 306 are byte-identical to the reference; `settings/appgeneral.html` differs only in the encoding of the "Norwegian Bokmål" label (checked 2026-10-04). Only static files inside the chosen directory are served, with no listing, no hidden files and no escape via symlink. Do not point it at a folder with private data: allowed HTML/JS/JSON and other resources are available without signing in. UI files are not included in the Couch binary or repository.

The alternative is `-web-upstream http://192.168.1.11:8096`: `/web/*` fetches the static files of the source Emby via GET/HEAD. Tokens, cookies, the request body and arbitrary query parameters are not passed upstream; redirects are not followed. At most 16 requests go to Emby at once; the rest wait up to 10 seconds for a free slot and then get 503 with `Retry-After`; a file larger than 32 MiB is not served. There is no cache. This mode requires a reachable Emby. `-web-dir` does not contact it for resources. In both modes the UI is served with `Content-Security-Policy: connect-src 'self'`, so the browser lets the client's fetch, XHR and WebSocket reach only Couch. This blocks the Emby Premiere registration check that Emby Web makes on every load, which would send the Couch ServerId, DeviceId, device name and app version to `https://mb3admin.com/admin/service/registration/validateDevice`; the client logs `getRegistrationInfo failed`, shows the "Get Emby Premiere" button and keeps working (#89).

The `-web-dir` and `-web-upstream` options are mutually exclusive. Without either, only the API and the information at `/` are available. In all modes, authentication, the catalog and video are served by Couch.

Other options: `-listen` (default `127.0.0.1:8097`), `-data` (`./data`), `-name` (`Couch`), `-ffmpeg-threads` (`0`), and `-metadata-language` and `-metadata-refresh` (see [Metadata](#metadata)). `-ffmpeg-threads N` caps the decoder and `libx264` encoder threads of each transcode at N; remux is not affected. FFmpeg sizes them from the host's CPUs, ignoring a container CPU quota, so by default (`0`) Couch caps them at the quota (Go's `GOMAXPROCS`: the quota rounded up to whole CPUs, at least 2) and logs `FFmpeg transcode threads follow the CPU quota`; without a quota FFmpeg keeps its own count. Under a quota the cap halves transcoding memory and brings the first segment forward (#92, [VALIDATION](docs/VALIDATION.md), [BASELINE](docs/BASELINE.md)). `-hwaccel` encodes transcodes on the GPU instead of with `libx264`: `vaapi` (Intel and AMD through VA-API), `qsv` (Intel Quick Sync), `nvenc` (Nvidia) or `amf` (AMD AMF); `-hwaccel-device` is the DRM render node for `vaapi` and `qsv` (default `/dev/dri/renderD128`). Decoding, scaling and subtitle burn-in stay on the CPU, so every source that `libx264` transcodes reaches the GPU encoder. At startup Couch encodes a short test pattern with the chosen encoder and refuses to start with FFmpeg's error if it fails (no device, driver or encoder in this FFmpeg build). Only `vaapi` is verified, on an AMD Radeon 780M (radeonsi), the target hardware: every transcode file of the agreed set passes in Emby Web, including the 4K source, and a transcode takes less than half the CPU and memory of `libx264` at a similar picture ([BASELINE](docs/BASELINE.md), "VA-API"); `qsv`, `nvenc` and `amf` follow FFmpeg's documented options and have not run on their hardware (#28). `-tonemap` (default `auto`) decides what a transcode does with HDR video (PQ: HDR10 and Dolby Vision; HLG): `auto` tone-maps it to SDR BT.709 with libplacebo on the GPU when Vulkan works, `software` does so with `zscale` on the CPU otherwise, and `off` encodes the HDR picture as it is and keeps its colour tags, as the reference Emby does by default (#125), so a client that ignores the tags shows it washed out. At startup Couch tone-maps a short test pattern and logs `HDR tone mapping method=libplacebo|zscale|off`; `software` refuses to start if this FFmpeg has no `zscale`, and each transcode of an HDR source names its method in `HLS job ended` (`tonemap=`). The GPU path needs a Vulkan driver: the VA-API image below has Mesa's for AMD; it is verified on the Radeon 780M, where VA-API itself cannot tone-map. libplacebo refuses a software Vulkan device such as lavapipe, so `auto` never tone-maps on the CPU. A burned-in image subtitle is overlaid after tone mapping, so it keeps its colours. Dolby Vision without an HDR10 or HLG base layer (profile 5) is tone-mapped only by libplacebo, which applies its Dolby Vision metadata; `zscale` leaves it as it is. On 18 s of the 4K HDR10 file R09 it adds a fifth to a third to a VA-API encode, which stays faster than real time on 2 CPUs; software tone mapping doubles a `libx264` encode, about 0.3× real time on 2 CPUs ([BASELINE](docs/BASELINE.md), "HDR tone mapping"). Item pages report the source's dynamic range as Emby does (`VideoRange` `HDR 10` or `DolbyVision`, `ExtendedVideoType` `Hdr10` or `DolbyVision`, `ColorTransfer`, `ColorPrimaries`, `ColorSpace`), and the library filter lists these types; the HLG values (`HLG`, `HyperLogGamma`) and the descriptions of Dolby Vision profiles other than 8.1 are not captured from Emby. The `-media-dir` scan enables HLS, so without it `-hwaccel` and `-tonemap` are not checked or used. Hardware encoders have a minimum frame size (128×128 on AMD VCN). The default listener is local; the container and the service listen on port 8097 of every address, for the LAN. TLS and running behind a reverse proxy are not configured. On a graceful shutdown (SIGINT, SIGTERM) Couch writes a `Couch stopped` line: its own CPU time and peak resident memory (`cpu`, `peak_rss_kib`) and, separately, the total time and the highest peak of finished FFmpeg and FFprobe child processes (`children_cpu`, `children_peak_rss_kib`) over the whole run.

### Container

The container is the main way to run Couch on the home server; [docs/INSTALL.md](docs/INSTALL.md) runs the binary as a systemd service instead. The [Dockerfile](Dockerfile) builds the image: a static `couch` on Alpine 3.24 with FFmpeg/FFprobe 8.1 (`fd` protocol, `libx264`, `aac`). The process runs as user `couch` (UID 10001), keeps its state in the `/data` volume and listens on `:8097`.

[deploy/compose.yaml](deploy/compose.yaml) runs it with Docker Compose. It builds the image from this checkout and restarts Couch after a crash and when the host boots. State goes to the `couch_data` volume. The media folder is mounted read-only at `/media` and becomes the Movies and TV Shows libraries on the first start; more folders below it are added in Emby Web. Emby Web is mounted read-only at `/web`, and Couch is published on port 8097 of every host address. Both folders must be readable by UID 10001. The settings live in `deploy/.env`; start from [deploy/.env.example](deploy/.env.example). First start:

```sh
cd deploy
cp .env.example .env    # set COUCH_MEDIA and COUCH_WEB
docker compose build
read -rsp 'New Couch user password: ' couch_password; printf '\n'
printf '%s\n' "$couch_password" | docker compose run --rm -T couch -init -username viewer
unset couch_password
docker compose up -d
```

Then open `http://HOST:8097/` from a device on the LAN. `COUCH_ARGS` in `.env` adds options such as `-rescan-interval 30m`, and the TMDb and TheTVDB keys go there too. To take Emby Web from a running Emby instead, replace the `/web` volume and `-web-dir /web` in `compose.yaml` with `-web-upstream http://192.168.1.11:8096`. Logs: `docker compose logs -f`. Rescan: `docker compose kill -s HUP couch`.

VA-API on an AMD or Intel GPU: uncomment the three lines at the end of `.env.example` in your `.env`. They add [deploy/compose.vaapi.yaml](deploy/compose.vaapi.yaml), which builds the image with Mesa's VA-API drivers and its Vulkan driver for HDR tone mapping (`VAAPI=1`, 565 MB instead of 213 MB) and passes `/dev/dri/renderD128` with the host's `render` group, and `-hwaccel vaapi`.

Upgrade: take a backup (below), then build the new image and recreate the container. Couch upgrades the database on its first start, keeps the media index (a `catalog.json` from an earlier release is imported into the database and left in place for going back) and refuses a database from a newer version without changing it. Tagging the old image first allows going back: point `image:` at `couch:previous` and restore the backup.

```sh
docker tag couch:latest couch:previous
git pull
docker compose build --pull
docker compose up -d
```

Backup and restore (see `-backup` in "Storage and limitations"). The copy holds password and token hashes, so keep it private:

```sh
docker compose exec couch couch -data /data -backup /data/backup
docker compose cp couch:/data/backup ./backup-2026-11-01
docker compose exec couch rm -r /data/backup

docker compose stop couch
docker compose run --rm --no-deps --user root -v ./backup-2026-11-01:/backup:ro --entrypoint sh couch \
  -c 'rm -f /data/couch.db /data/couch.db-journal /data/user-image-* && cp /backup/* /data/ && chown couch:couch /data/*'
docker compose start couch
```

Client addresses: with Docker's default port publishing (iptables), Couch sees the address of each LAN client, so the sign-in limit per address and the activity log name the real client. Connections to `127.0.0.1` on the host and from other containers arrive through `docker-proxy` from the network's gateway (for example `172.19.0.1`) and share one sign-in limit. A port forwarder that proxies every connection, such as rootless Podman's default, would hide all clients behind one address the same way; `network_mode: host` avoids it. Podman has not been checked.

Without Compose, the same image runs with `docker run` or `podman run`; arguments after the image name replace `-listen :8097`, and `-data /data` is set in the image:

```sh
docker build -t couch .
docker run -d --name couch --restart unless-stopped -p 8097:8097 -v couch-data:/data -v /srv/media:/media:ro -v /opt/emby-webui:/web:ro couch -listen :8097 -media-dir /media -web-dir /web
```

`scripts/check-container.sh IMAGE` checks the image: `-init`, scanning an MKV H.264 + AC3 and remux to HLS (FFprobe reads `h264` + `aac`), and shutdown with exit code 0. Docker is used by default, Podman via `CONTAINER=podman`. Requires `curl` and `jq`.

## Movie, TV series, music and photo catalog

Libraries are managed by the administrator on Emby Web's Library page (Manage Emby Server → Library) and need FFprobe with support for the `fd` protocol. Folders can be chosen only below a media root, given with `-media-root` (repeatable):

```sh
./bin/couch -media-root /absolute/path/to/media -web-dir ../emby-webui
```

- **Libraries:** a library has a name, a content type and one or more folders. Movies, TV shows, music and home videos & photos are supported; other content types are refused. A movies library holds the videos that are not recognized episodes, a TV shows library the episodes with their series and seasons, a music library the audio files with their albums ([Music](#music)), a home videos & photos library the pictures and every video with their folders as albums ([Home videos and photos](#home-videos-and-photos)), so one folder may serve one library of each type. A folder is read only for the files its libraries hold: audio files only for a music library, pictures only for a home videos & photos library, videos for the others. A folder that is, contains or lies in a folder of another library of the same type is refused, so a file is never listed twice. The libraries are stored in `couch.db`, in their order, and come back after a restart and a backup restore.
- **Library page:** New Library, rename, delete, and in the library editor add and remove folders. The folder browser lists only the media roots and the folders below them, without hidden ones; a path outside a root, one with `.` or `..` components, or one whose symbolic links lead outside a root is refused. The library options in the dialogs (metadata fetchers, real-time monitoring and the like) are accepted but not stored: Couch's scanner and metadata sources are fixed. Network paths are refused. A new or changed library is listed at once; its new folders fill when the scan it starts finishes, and open screens refresh (`LibraryChanged`).
- **`-media-dir`** is a shortcut for the first start: when no libraries have been stored, it creates that directory's `Movies` and `TV Shows` libraries, with the IDs a `-media-dir` catalog has always had, and is a media root when `-media-root` is not given. After that the stored libraries win: changing or dropping `-media-dir` changes nothing, and removing every library does not bring them back.
- **Scans:** the first start scans before the HTTP server starts and saves the result as the media index in `couch.db`; later starts serve the saved catalog at once and rescan in the background. A missing, corrupted or outdated index is ignored and the libraries are scanned again; an index from before stored libraries, music libraries or photos is read, and the background rescan adds what it lacks; in an index from before HDR colour properties were probed (#125), videos are served as saved and probed again by the background rescan. A folder shared by two libraries is walked once. A rescan runs from "Scan Library Files" on the library page or the "Scan media library" scheduled task (Manage Emby Server → Scheduled Tasks), on `SIGHUP` (`kill -HUP <pid>`) and, if `-rescan-interval` is set (for example, `30m`, at least `1m`), periodically; by default there is no periodic scan. The task reports whether it runs and how the last scan ended, also over WebSocket (`ScheduledTasksInfo`) to the pages that ask; a running scan cannot be stopped. On a rescan, files with the same path, size and mtime do not go through FFprobe again; added, changed and deleted files become visible after the new catalog is published, and IDs of unchanged paths are kept. One scan runs at a time: a request during a scan starts another one after it. A folder that cannot be read, or that suddenly has no media files left (this is what an unmounted NAS volume looks like), keeps its previous files while the other folders are updated; the scan is reported as failed and the log names the folder (`failed_folders`). Exceeding a limit keeps the whole previous catalog, and `Media rescan failed; keeping the previous catalog` is written to the log. After each publish the index is updated in one short transaction that writes only the files that were added, changed or deleted. After publishing a changed catalog, Couch sends `LibraryChanged` over WebSocket to all connections: added, changed (size, mtime, duration) and deleted IDs, their parent folders and the affected libraries; open Emby Web screens (the library, "Recently Added" on the home screen) refresh themselves. The field names are taken from the client handler; a reference Emby message has not been captured. Without libraries FFprobe is not required. Source files are not modified.

The structure `Show/Season 01/Show.S01E02.mp4` inside a TV shows library's folder creates a series, a season and an episode. The season number in the folder and the name must match; `Season 00` is supported. Other names remain movies. Movie IDs do not change; series/season IDs are stable while the path is unchanged. Item pages, search, Seasons/Episodes and direct episode delivery are supported; "Play" on a series plays the episodes in order in the client queue. `Shows/NextUp` returns, for each started series, the episode after the furthest one watched; series are ordered by last watched, and `Season 00` specials are not counted. The Continue Watching row on the home screen (`Sections/resume/Items`, the section declares `IncludeNextUpInResume`) and `Items/Resume` add these episodes to the started items (as in the reference Emby, `Items/Resume` adds them even without `IncludeNextUp`; only `IncludeNextUp=false` excludes them — this is an assumption, not captured); when sorting by date played, the episode gets the last-played date of its series. This order is an assumption: the Emby response has not been captured. Alternative naming schemes are not implemented. Home screen row titles follow `X-Emby-Language` for Russian, German, French, Spanish and Italian (Emby Web client wording); for other languages they are English. Translations live in `internal/server/locales/<language>.yaml` (key: text, keys are Emby Web strings) and are embedded in the binary; `en.yaml` contains all keys and serves as the fallback language. A new language is a new file; a test checks that it has no keys missing from `en.yaml` and no empty values. Item titles come from metadata in its language (`-metadata-language`), not from `X-Emby-Language`.

- Extensions: mp4, m4v, mkv, webm, avi, mov, mpg, mpeg, ts, m2ts, wmv, ogv for videos, which need a detected video track; mp3, flac, m4a, aac, ogg, oga, opus, wav, wma, aiff, aif for music, which needs an audio track; jpg, jpeg, png, gif, webp, bmp for photos, which must decode as that picture format. Broken files are skipped and counted in the log without paths.
- The title comes from metadata ([Metadata](#metadata)) or, without it, from the file name; FFprobe provides the duration, codecs, frame dimensions, and audio and subtitle tracks.
- The ID depends on the absolute library folder and the relative file path: it persists across restarts and changes on move/rename. `DateCreated` is the time Couch first saw the path: for files found by the first scan of a folder, the file modification time; for files a later rescan finds, the time of that rescan. Latest and sorting by DateCreated use it. The date is kept in the index across restarts and backups.
- The catalog is kept in memory and, as the media index (what FFprobe found and when each path was first seen), in the `catalog` table of `couch.db`. Releases before schema version 11 kept the index in `catalog.json`; the first start of a newer one imports that file into the database and leaves it, so the previous release can still use it after going back. Couch no longer reads it once the database holds an index; delete it when going back is no longer needed. A folder without files is kept in the index, and a folder that cannot be read keeps its entries while it stays in a library. A start with a saved index probes only files whose size or mtime changed while Couch was stopped. If a folder comes back empty at startup (an unmounted volume), its saved videos stay published. A file change that keeps the size and mtime is not detected by a rescan.
- The `Media scan complete` and `Media rescan complete` lines report the videos (`videos`), audio files (`tracks`) and photos (`photos`) published, how many times FFprobe ran in this scan (`probes`; unchanged files are not probed on a rescan), its total CPU time (`probe_cpu`) and the highest peak memory of a single run (`probe_peak_rss_kib`).
- Limits, across all libraries: 10,000 video files, 10,000 audio files, 50,000 photos, 100,000 traversal entries, depth 64, scanning up to 10 minutes; one FFprobe at a time, up to 15 seconds and 1 MiB of JSON per file. Exceeding a global limit stops startup (on a rescan, keeps the previous catalog) instead of publishing an incomplete catalog. The timeout does not guarantee interruption of hung OS file I/O.
- Symbolic links and special files are not traversed. Files are opened inside `os.Root`; FFprobe receives a descriptor, not a path. Only the `fd` protocol is allowed, with no network requests and no opening of neighboring files. This is an access restriction, not a full sandbox for FFprobe.

Supported: search by name (title, original title or file name), ParentId, Recursive, IDs/exclusions, media types, `CollectionTypes` (`movies` — movies and the Movies library, `tvshows` — series, seasons, episodes and the TV Shows library, `music` — albums and tracks, `homevideos` — photo albums, photos and home videos; other types return an empty page), `CanEditItems` (`true` — the user's own playlists and, for an administrator, the items they may add to a collection and the collections), filters on FFprobe data — `Containers`, `VideoCodecs`, `AudioCodecs`, `AudioLayouts`, `SubtitleCodecs`, `AudioLanguages`, `SubtitleLanguages`, `ExtendedVideoTypes` (a series and season match by their episodes) — and basic filters. The library "Filter" dialog gets values from `/Containers`, `/VideoCodecs`, `/AudioCodecs`, `/AudioLayouts`, `/SubtitleCodecs` and `/StreamLanguages` (by `StreamType`) within `ParentId` and `IncludeItemTypes`, paginated (`StartIndex`, `Limit` up to 1000, as for Items: the client checks each list with a `Limit=1` request). `/Genres`, `/Studios`, `/Tags`, `/OfficialRatings`, `/Years` and `/Persons` list the values of the items' metadata the same way, and Items filters by `Genres`, `Studios`, `Tags`, `OfficialRatings` (names joined with `|`), `Years`, `GenreIds`, `StudioIds`, `TagIds` and `PersonIds` (with `PersonTypes`); a series matches by its own metadata, not its episodes'. A genre, studio, tag or person opens as an item page listing its items. A person page's credit tabs (`Persons/{Id}/Credits`) list, per credit type (Actor, Director, Writer and so on, in Emby's order), the items of the user's libraries that credit the person, newest first; an episode credits its series once. Emby fills these tabs from its metadata provider, so its list can also hold titles outside the library; Couch does not. Emby Web shows a credit's overview when it is clicked, not its item page. People cannot be marked favorite yet, so the home "Favorites" tab lists no people (#80); artists can ([Music](#music)). Sorting is a comma-separated list of fields from Name/SortName, DateCreated, DatePlayed, DateLastSearched, Runtime, ParentIndexNumber, IndexNumber, SeriesSortName, IsFolder (folders first), Filename, TotalBitrate, VideoCodec, Container, Size, Resolution, Framerate, PlayCount, SeriesDatePlayed (last watched episode of a series or season), DateLastContentAdded (newest episode), OfficialRating, ProductionYear, PremiereDate, CommunityRating, CriticRating, Director (first director), LastContentPremiereDate (newest episode premiere), ListItemOrder (playlist order), DateModified (last change of a playlist; file mtime for other items), Album, AlbumArtist, Artist (first artist), Bitrate (as TotalBitrate) and Random (shuffle; subsequent keys do not change the order). Name sorts by the metadata sort title or title; episodes sort by season and episode number first. ChannelNumber and Composer are accepted and do not change the order: Couch has no channels and reads no composer tag, so the next key decides (#79). Fields are compared in order; `SortOrder` gives one order per field, and its last value applies to the fields after it. `Items/Prefixes` takes the same query and returns the first letters of the matching sort names (`[{"Name":"A"},…]`) for the A–Z jump bar shown on lists of more than 30 items; a letter then sends `NameStartsWithOrGreater` (#124). `MinPremiereDate` and `IsUnaired` compare the metadata premiere date; an item without one never matches a premiere bound and counts as aired. `IsSpecialEpisode` selects `Season 00` episodes. `LiveTv/Programs` and `Movies/Recommendations` are always empty: there is no Live TV and no recommendations. A page contains up to 100 items by default, Latest up to 20, and at most 1000: a larger `Limit` (Emby Web's "play from here" on a song asks for 5003) is reduced, not rejected. Unknown filters/sorts return 400. Position, play count, and "played" and "favorite" marks are saved in the user state. Marking a series or season as played sets or clears the mark on all its episodes; a series or season counts as played when all episodes are played, and reports `UnplayedItemCount`. "Remove from Continue Watching" (`HideFromResume`) resets the saved position and marks the item hidden so it does not come back as the next episode; the mark is cleared on the next playback or with `Hide=false`, and the position is not restored. A home screen row returns at most 1000 items: a larger `Limit` (the item menu requests 5000) is reduced, not rejected.

### Metadata

Titles, overviews and the other descriptive fields come from local `.nfo` files and, when their API keys are set, from TMDb and TheTVDB, in Emby's order: a `.nfo` wins where it has a value, and the providers fill the rest (#101).

- **`.nfo` files** (Kodi/Emby format) are read next to the media: `<file name>.nfo`, then `movie.nfo` in the movie's folder; `tvshow.nfo` in the series folder; `season.nfo` in the season folder; `<file name>.nfo` for an episode. Read: title, original and sort title, plot, tagline, year, premiere date, genres, studios, tags, community rating (`<ratings>` default or `<rating>`), critic rating, `<mpaa>`, actors, directors, writers (`<credits>`), and the IMDb, TMDb and TheTVDB IDs (`<uniqueid>`, `<imdbid>`, `<tmdbid>`, `<tvdbid>`, or a provider link). A file of up to 1 MiB is read; an unreadable one keeps what was stored. Images referenced in a `.nfo` are not used; local images are found as before.
- **Online providers** are on only when their key is set, in the environment so that it does not show in the process list: `COUCH_TMDB_API_KEY` (a TMDb v3 API key or v4 read access token) and `COUCH_TVDB_API_KEY` (a TheTVDB v4 project key). Without a key Couch sends that provider nothing. Movies are looked up on TMDb; series on TheTVDB, then TMDb, which also fills what TheTVDB lacks; episodes by their series' IDs. A lookup uses the provider IDs from the `.nfo`, else the title and year from the `.nfo` or the cleaned file or folder name (`The.Movie.2010.1080p` → "The Movie", 2010). Of TMDb's search results, one whose title or original title equals the query wins, else the most popular: TMDb ranks by the title in the metadata language, so an English file name searched in Russian can rank a minor title first. Provider requests send the title, year or ID and the API key; they are logged without titles. Requests are spaced: at most 20 a second to TMDb, 10 to TheTVDB and 50 to the image servers. A 429 answer is repeated after its `Retry-After` (at most a minute, three times). A rejected key, five failed requests in a row, an image that could not be saved or metadata that could not be stored stop the lookup; it is tried again after 5 minutes, doubling up to an hour, without waiting for a rescan. An item whose lookup or image failed is fetched again then.
- **Language:** `-metadata-language` (`en` by default; `ru`, `de`, `fr`, `es`, `it`) selects the language of titles and overviews and the country of parental ratings.
- **Images:** the provider's poster and backdrop are downloaded as Primary and Backdrop images into `metadata/` in `-data` (JPEG or PNG, up to 8 MiB); a local image wins. TMDb posters and episode stills are fetched 780 pixels wide and backdrops 1280 wide, about 110 KiB each. TheTVDB serves only originals, so every downloaded image is scaled down to at most 1280 pixels wide (landscape) or 780 (portrait) and saved as JPEG at quality 85, unless that is not smaller or the image has transparency: a TheTVDB backdrop drops from about 460 to 155 KiB, a poster from 160 to 80 KiB. The folder has no size limit. Images no item uses are deleted after a complete lookup.
- **Storage and refresh:** metadata is stored in `couch.db`, so a restart reuses it without reading or asking again. Each scan and rescan reads a `.nfo` whose size or mtime changed and looks up items that are new, whose `.nfo` changed their lookup, or whose stored images are missing. `-metadata-refresh` (for example `720h`, at least `1h`; `0`, the default, never does) looks up again what was fetched longer ago; Couch checks hourly. An item no provider found is not asked again until then. A rescan that finds the same items does not interrupt a running lookup; its `.nfo` files are read when the lookup ends. While a lookup runs, the results are published every 10 seconds. With 10,000 movies the stored metadata takes about 44 MiB of memory. The media directory is never written to.
- **Administrator actions** on an item's "…" menu, administrators only (#115):
  - **Refresh Metadata** reads the item's `.nfo` again and, with a provider key, fetches its online metadata again at once, whatever `-metadata-refresh` says. A series covers its seasons and episodes, a collection its items, a library everything in it. It runs in the background like the "Refresh metadata" task.
  - **Identify** searches by title and year, or by a TheMovieDb, TheTVDB or IMDb ID: movies with TMDb, series with TheTVDB and then TMDb, up to 10 results per provider. The chosen result's IDs are stored in `couch.db`. From then on the item is looked up by them alone, and the provider's metadata wins over the `.nfo` (a series' episodes follow its new IDs). The dialog's poster preview is fetched through Couch, from the providers' image hosts only. Without a provider key, or when the provider does not answer, the search shows one result naming the problem, since the dialog shows no server error; that result cannot be applied.
  - **Remove Identification** drops the stored IDs and what they fetched; the item goes back to its `.nfo` or file name and is looked up again.
  - Identify and Remove Identification on a collection answer "Couch identifies movies and series, not collections."
  - **Metadata Manager** shows the library tree and an item's fields. Couch does not edit metadata, so saving is refused (`400`, and Emby Web shows no message): change the `.nfo`, or use Identify.
- Not implemented: editing metadata and images, person images and biographies, season metadata from providers, and marking a person favorite. Items report `CanEditItems: true` to an administrator so that Emby Web offers "Add to Collection" ([Collections](#collections)); that also opens the metadata and image editors, which show the item's fields and images but refuse a save or an image change (`400`). Other users get `CanEditItems: false` and no editors, except on their own playlists ([Playlists](#playlists)).

### Collections

An administrator groups movies, series, seasons and episodes into collections (Emby's BoxSets) from Emby Web:

- **Create and fill:** "Add to Collection" in an item's menu, also for several items selected at once, adds to an existing collection or creates a new one. "Remove from Collection" on an item of a collection, or on the collection under an item's "Included In" row, takes the item out. Edit Metadata on a collection renames it; its other fields are not stored. Delete removes the collection, never its items or files.
- **Where they show:** a "Collections" library in My Media once a collection exists, a Collections tab in the Movies and TV Shows libraries (those with an item of that library), an item page's "Included In" row, and Favorites. A collection lists its items by release date, then title. "Play" plays its movies and the episodes of its series in that order. "Mark Played" marks them all. The view option "Group into collections" shows a collection in place of its items.
- **Who sees them:** collections are shared by all users and stored in `couch.db`. A user sees a collection when they can see one of its items, and only those items. Only an administrator sees an empty collection or changes one.
- **Moved files:** a collection keeps the ID of an item whose file moved or disappeared, hidden until the path returns.
- **Not implemented:** collection images (cards show a placeholder), collections from `.nfo` `<set>` or TMDb, a manual item order, and "View missing items", which is always empty. Up to 1,000 collections of 10,000 items each.

### Playlists

Every user keeps their own playlists of movies, episodes, music tracks, home videos and photos in Emby Web:

- **Create and fill:** "Add to Playlist" in an item's menu, also for several items selected at once, adds to an existing playlist or creates a new one. A series or season adds its episodes in order, an album its tracks by disc and track number (a track without a disc number counts as disc 1). A playlist of tracks only reports `MediaType: Audio`, one of photos only `Photo` (played as a slideshow), any other `Video`. If the playlist already holds an item, Emby Web asks whether to add it again or skip it; a playlist may hold an item more than once.
- **Edit:** on the playlist page, drag an item to reorder it, or "Remove from Playlist". Edit Metadata renames the playlist; its other fields are not stored. Delete removes the playlist, never its items or files.
- **Where they show:** a "Playlists" library in My Media once the user has a playlist, the Playlists section of the navigation menu, and Favorites. A playlist lists its items in playlist order, or in the sort order chosen on its page. "Play" plays them in that order. "Mark Played" marks them all.
- **Who sees them:** a playlist is private to the user who made it, administrators included, and is stored in `couch.db`. Deleting a user deletes their playlists. An entry whose item the user can no longer see is hidden.
- **Moved files:** a playlist keeps the ID of an item whose file moved or disappeared, hidden until the path returns.
- **Not implemented:** playlist images (cards show a placeholder) and shared playlists. Up to 1,000 playlists per user of 10,000 entries each.

### Music

A music library (content type Music on the Library page) holds the audio files of its folders (#104):

- **Tracks and albums:** the title, artists, album, album artist, track and disc numbers, year and genres come from the file's tags as FFprobe reads them (ID3, Vorbis comments, MP4 and the like, in any case); artists are split at `;`, genres at `;` and `/`. What the tags lack comes from the layout `Artist/Album/03 - Title.mp3`: the album from the folder, the album artist from the folder above it or else the first artist, the track number (and the disc in `1-03`) and the title from the file name. Tracks with the same album artist and album make one album, also across folders such as `CD1` and `CD2`; a file with neither an album tag nor a folder sits directly in the library. An album's year is its newest track's, and its genres are those of its tracks.
- **Emby Web:** the Music library's Suggestions, Albums, Album Artists, Artists, Playlists, Genres, Songs and Folders tabs; album pages by disc and track; artist pages with songs, albums and albums as a contributing artist (one who performs on an album without being its album artist); genre pages; search; Latest Music on the home screen, where new tracks show as their albums; and Continue Listening, the tracks with a saved position. An artist can be marked favorite and then shows under Favorites. Music does not go through the `.nfo` and online metadata lookups.
- **Playback:** Emby Web plays a track from `Audio/{id}/universal`, listing the containers and codecs the browser plays. A file that matches is served as it is, with ranges: in Chromium MP3, FLAC, AAC in M4A, Ogg Vorbis, Opus and WAV. Any other (WMA, ALAC, AIFF) is encoded once with FFmpeg to AAC in M4A, at 192 kbit/s or the client's lower `MaxStreamingBitrate` (at least 64 kbit/s) and at most two channels, then served from `<data>/transcode/audio` with ranges, so the player seeks in it; a request for HLS gets that file too. At most two encodes run at once; others wait up to 10 seconds and then get 503. An encode stops after 2 minutes. The 32 most recently played encoded tracks are kept, and the directory is cleared at startup and shutdown. Each encode logs an `Audio encode ended` line with its CPU time and peak memory. Without FFmpeg such a track is refused with a message. Position, plays and played marks are saved as for videos; marking an album played marks its tracks.
- **Instant Mix** from a track, album, artist, music genre or playlist plays the seed's tracks, then the other tracks that share an artist or a genre with them, from the libraries the user can see (#119). The first seed track leads and the rest are shuffled; a mix holds at most 200 tracks, or fewer if the client's `Limit` is lower (Emby Web asks for 5000). Emby Web asks `Items/{id}/InstantMix` for every kind of seed; `Albums/`, `Songs/`, `Playlists/{id}/InstantMix`, `Artists/InstantMix` and `MusicGenres/InstantMix` (`Id` or `Ids`) and `MusicGenres/{name}/InstantMix` answer the same way. A seed without tracks, such as a movie or a playlist of videos, makes an empty mix.
- **Not implemented:** composers, lyrics, online music metadata, music videos and audiobooks.

### Home videos and photos

A home videos & photos library (content type "Home videos & photos" on the Library page; Emby Web has no separate photos type) holds the pictures and videos of its folders (#105):

- **Photos:** jpg, jpeg, png, gif, webp and bmp files, read by their header without FFprobe: the size, and for a JPEG the EXIF orientation (a picture turned a quarter reports its width and height swapped) and `DateTimeOriginal` with `OffsetTimeOriginal` (UTC without it). A photo without that date is dated by its file's mtime. The date is its `PremiereDate` and `ProductionYear`, so photos sort by when they were taken. `poster`, `folder`, `cover`, `backdrop`, `fanart`, `clearlogo`, `logo`, `landscape` and `thumb` pictures and a video's own images (`Clip-poster.jpg` next to `Clip.mp4`) are images of their folder or video, not photos.
- **Videos:** every video of the folders, also one that a TV shows library would see as an episode, is a plain `Video` played like a movie, without the `.nfo` and online metadata lookups. Its ID differs from the movie's or episode's that a library of another type makes of the same file.
- **Albums:** each folder that holds a photo or video, at any depth, is a `PhotoAlbum` inside the album of the folder above it; files at the top of a library folder sit directly in the library. An album's image is its `poster`, `folder` or `cover` picture, else its first photo by file name.
- **Emby Web:** the library opens with Videos, Photos and Folders tabs. Clicking a photo opens the slideshow at that photo; clicking an album card plays its photos as a slideshow, as Emby Web does for every photo album. Latest on the home screen is titled "Latest from" the library's name. The "Enable photos" switch is on for a new library, and a library always shows its photos: the switch is not stored.
- **Delivery:** a photo is served as it is, with ranges, as its own Primary image (`Items/{id}/Images/Primary`), whatever `maxWidth` or `quality` the client asks for. Up to 64 MiB per photo; only its header is read, never its pixels.
- **Not implemented:** HEIC and RAW pictures, resized or cached thumbnails, a photo's camera and location data, and video thumbnails.

## Artwork

Primary images are read from local `.jpg`, `.jpeg`, `.png` files (lowercase extensions); without a local one, a poster or backdrop downloaded from an online provider is used ([Metadata](#metadata)). For videos and tracks the lookup order is: `<name without extension>-poster`, `<name without extension>`, then `poster`, `folder` and `cover` in the same folder. For series, seasons and albums: `poster`, `folder` and `cover` in their folder; an album's folder is that of its first track. A track or album without a local image uses the cover embedded in its audio file (an ID3 `APIC` frame, a FLAC `PICTURE` block, an M4A `covr` atom), or for an album its first track's by disc and track number: FFprobe reports its size and type while scanning, and the first request for the image copies it out with FFmpeg, unchanged, into `covers/` in `-data`, where the 1,000 most recently used are kept. Only JPEG and PNG covers within the limits below are served, and none without FFmpeg. A track without its own image names its album's in `AlbumPrimaryImageTag`. A photo is its own Primary image and has no other; a photo album without a local image takes its first photo's ([Home videos and photos](#home-videos-and-photos)).

The backdrop (item page background) is looked up the same way, by its own names: for videos `<name without extension>-fanart`, `<name without extension>-backdrop`, then `backdrop` and `fanart` in the same folder; for series/seasons, `backdrop` and `fanart` in their folder. One image per item (`Images/Backdrop/0`), in `BackdropImageTags`. The logo (`Logo`: `<name>-clearlogo`, `<name>-logo`, then `clearlogo`, `logo`) and the landscape image (`Thumb`: `<name>-landscape`, then `landscape`, `thumb`) are looked up the same way; they go into `ImageTags`. A season or episode without its own backdrop, logo or Thumb gets the series image, as in Emby: `ParentBackdropItemId` and `ParentBackdropImageTags`, `ParentLogoItemId` and `ParentLogoImageTag`, `ParentThumbItemId` and `ParentThumbImageTag`. A season and an episode always get the series image in `SeriesPrimaryImageTag`, as a season does in the reference: Emby Web shows it on an item card without its own image, in the "Now Playing" bar and in the system media controls.

Limits: file up to 8 MiB, header up to 1 MiB, side up to 16,384 pixels, area up to 32 million pixels. Access is restricted to the media library root; the server does not decode pixels. The original is served with no resize, quality conversions or overlays. The `.jpg`/`.jpeg`/`.png` names in an item's folder are read as one list and cached until the folder mtime changes (a list taken within two seconds of the mtime is not reused); a new image added without changing the folder mtime is not visible until its next change or a restart.

Emby Web gets a signed ImageTag and passes it in `tag` without an API token. The link authorizes only that specific image revision and is valid until logout/session expiry; a graceful restart keeps it. Do not publish such links: they are limited access keys. A regular API token is also accepted. Authorization is checked before a 304 response; the cache is private, with mandatory revalidation. The revision and weak ETag depend on the path, size and mtime, not the content: a replacement that keeps the size/mtime is not detected.

Changing the password: `POST /Users/{id}/Password` with `CurrentPw` and `NewPw` (12–1024 bytes) checks the current password under the same rate limit as sign-in; the current session remains, the others are revoked. Emby Web 4.10 hides the current password field for servers from 4.8.0.38 and sends it empty. Per decision #46, Couch still requires the current password: an empty one is rejected with 400, a wrong one with 401 (a text message); the profile form shows the client's generic error "Invalid username or password", and the session is kept. An administrator sets another user's password with `NewPw` alone, or removes it with `ResetPassword`; that user's sessions are revoked. Removing one's own password is refused, since the user could not sign in again.

A user's avatar is uploaded and deleted on their Emby Web profile page; an administrator also sees other users' avatars. JPEG and PNG are accepted with the same limits as artwork; the file is stored as uploaded, in the `-data` directory next to `couch.db` (`user-image-<revision>`). The revision is a hash of the content. `PrimaryImageTag` is signed the same way as an artwork ImageTag and is not valid for item images.

## Playback

Couch serves the source file via Direct Stream: GET/HEAD, Range, 206/416 and Resume are supported. If the client does not accept the file as is, but its HLS profile (`TranscodingProfiles`: `Protocol=hls`, `Container=ts`) accepts the video codec, Couch does a remux to HLS: video is copied without re-encoding, audio is copied if the profile accepts its codec, otherwise it is encoded to AAC (channels up to `MaxAudioChannels`, stereo without it). PlaybackInfo returns `TranscodingUrl` (`/videos/{id}/master.m3u8?...`, the token in the link, as for the stream), `TranscodingSubProtocol=hls`, `TranscodingContainer=ts`. The `main.m3u8` playlist is a VOD for the whole movie; MPEG-TS segments are cut at the source keyframes, no shorter than 6 seconds; on the first request Couch reads the keyframes from the container index (the `Cues` of MKV and WebM, the sample tables of MP4 and MOV: the header and the index only, 29 KB of a 1.2 GiB MKV) and checks its first and last keyframe with FFprobe; without a usable index (AVI, MPEG-TS, an MKV without `Cues`, keyframes more than 12 s apart in the index) FFprobe finds them by seeking every 2 seconds, reading a few packets per seek, and MPEG-TS (where a seek does not land on a keyframe) is read in full (the list is cached in memory for up to 64 files; PlaybackInfo starts the read in advance, for a remux only, unless it has `IsPlayback=false`, which Emby Web sends for an item page; at most two files are read at once, the rest wait in a queue). Seeking beyond what is ready restarts FFmpeg from the needed segment, with timestamps matching a continuous pass. Limits: two remux sessions and one transcode session at a time (the next one gets `RateLimitExceeded`, an HLS request gets 503), segments are stored in `<data>/transcode` (cleared at startup and shutdown), a session holds up to 2 GiB; FFmpeg is paused (SIGSTOP) once it is 10 segments ahead and resumes when the client catches up; old segments are deleted. A session ends on `Sessions/Playing/Stopped`, `Videos/ActiveEncodings/Delete` (`POST`, or `DELETE Videos/ActiveEncodings`; without `PlaySessionId`, all of the caller's sessions), logout, or after a minute without requests. Without FFmpeg in PATH, remux and transcode are disabled. If the HLS profile does not accept the video itself (codec, profile, level, bitrate; for example, HEVC 10-bit or MPEG-4 Part 2 for a browser) but accepts `h264`, the video is encoded to 8-bit H.264 (`libx264`, `veryfast`, CRF 23) at the same size (an odd dimension is rounded down to even); `TranscodingUrl` contains `VideoCodec=h264` and `VideoBitrate`, the `-maxrate` ceiling: the source bitrate; with a client limit, no higher than the limit minus 192 kbit/s for audio (no less than half the limit and 100 kbit/s); without data, 8 Mbit/s. `LessThanEqual` conditions on `Width`, `Height` and `VideoBitrate` from the `h264` codec profile (without `ApplyConditions`) constrain encoding: the picture is downscaled preserving the aspect ratio (`MaxWidth`/`MaxHeight` in the URL), and the bitrate is capped at the lower of the ceilings. Emby Web sets `Width` to 1920 if the browser does not decode 4K smoothly. Audio is handled as in remux. Segments are 3 seconds long, as in Emby, counted from the first video frame: the encoder places a forced keyframe at each, so seeking by restart produces the same segments, and no keyframe list is read (FFprobe reads only the header and the first packet). The `VideoLevel` condition of the same profile downscales the picture to the largest frame for that level (MaxFS per H.264 Table A-1: for example, 4K at level 4.2 is about 1980×1114); the bitrate ceiling does not exceed the level's MaxBR for the High profile (×1.25); the level in the stream is chosen by `libx264`. The level's macroblock rate (MaxMBPS) is also respected by downscaling the frame at the source frame rate: 1080p60 at level 4.1 is about 1358×764, and the frame rate is preserved. Restarting encoding from the middle decodes from the keyframe of the previous segment and trims to the start of the needed one with the `trim`/`atrim` filters, so even HEVC with open GOPs in MPEG-TS produces the same segments as a continuous pass (#81); with copied audio (which cannot be filtered) a direct `-ss` to the segment remains, and for such HEVC in MPEG-TS a restart may start later than planned. With `-hwaccel` the video is encoded by the GPU at the same quality target, capped at the same `VideoBitrate`, and each forced keyframe is an IDR frame. Otherwise the response is `NoCompatibleStream`. With FFmpeg, the user policy allows video transcoding and remux (`EnableVideoPlaybackTranscoding`, `EnablePlaybackRemuxing`), and PlaybackInfo for a direct stream reports `SupportsTranscoding` if HLS can also serve it: this makes Emby Web show the "Quality" item in the player, and the chosen bitrate arrives in a new PlaybackInfo with `MaxStreamingBitrate` (#72). Such a PlaybackInfo names the current playback in `CurrentPlaySessionId`: Couch ends its HLS session (the client deletes it only after the response, and switching from one transcoded quality to another would otherwise hit the limit) and adds the new `PlaySessionId` to the same playback. After the switch, Emby Web sends progress and stop under the new ID if the stream changed, and under the old one if not; both are accepted, and the position is saved (#73). Compatibility still depends on the container, codecs and client. Seek previews are not generated: `ThumbnailSet` returns an empty set. The "Download" command (`Items/{id}/Download`) serves the source file as an attachment; the file name is the item title with the source extension. Each FFmpeg run, when it finishes, writes an `HLS job ended` line to the log: the item ID, what was done with video (`video`: `copy` or `h264`, with the `encoder`, such as `libx264` or `h264_vaapi`, when encoded) and audio (`audio`: `copy`, `aac` or `none`), the number of completed segments, FFmpeg CPU time (`cpu`, user + system) and its peak resident memory (`peak_rss_kib`), separately from Couch's own usage.

PlaybackInfo reads parameters from the query and JSON, including JSON sent as `text/plain`. It takes into account `EnableDirectStream`, bitrate/channel limits, the source and the audio track (Emby Web in Chromium accepts a non-first track only via remux to HLS: its profile sets an `IsSecondaryAudio` condition); it rejects conflicting values, another user's UserId and invalid indexes. `StartTimeTicks` is validated, but the file is not trimmed: with direct delivery the client seeks via Range.

The profile is checked against DirectPlayProfiles, ContainerProfiles and CodecProfiles/ApplyConditions. Supported comparisons are Equals/NotEquals/EqualsAny/LessThanEqual/GreaterThanEqual and the main video/audio parameters: resolution, codec level/profile/tag, bitrate, frame rate, channels and sample rate. Missing required metadata is not considered compatible; optional conditions without metadata are skipped. A condition is required by default. A missing DeviceProfile keeps discovery mode; an explicitly empty one does not allow playback.

On incompatibility the response contains `ErrorCode=NoCompatibleStream` with no stream URL. A refusal (`NoCompatibleStream` or `RateLimitExceeded`) is logged as a `Playback refused` line with the item ID, error code, container, video and audio codec, and flags for the presence of a DeviceProfile (`profile`) and FFmpeg (`hls`), without paths or tokens. External subtitles next to the video (`Movie.srt`, `Movie.ru.srt`, `Movie.en.forced.srt`, `Movie.ru.sdh.srt`; also `.vtt`) are added during scanning as tracks after the embedded ones: the language is the first tag of 2–3 Latin letters, and `forced`, `sdh`/`hi`/`cc` and `default` set flags; letter case in the name does not matter; if a name matches two videos, the file goes to the video with the longer name, and videos with the same name (`Movie.mp4` and `Movie.mkv`) both get it. SRT with CR, CRLF or LF line endings is supported. PlaybackInfo returns them with `DeliveryMethod=External` and a WebVTT link (`/Videos/{id}/{source}/Subtitles/{index}/Stream.vtt`, the token in the link, as for the stream; the same file is served at `/Items/{id}/{source}/Subtitles/{index}/Stream.vtt`); SRT is converted to WebVTT on the fly. Only UTF-8 (with or without BOM) is supported: a file in another encoding (for example, Windows-1251) is not served, and `Subtitle unavailable` is written to the log. Up to 32 files per video, up to 10 MiB per file. Embedded text subtitles (SubRip, mov_text, WebVTT, ASS/SSA) are served at the same link: on request, FFmpeg extracts the track to WebVTT through a pipe, without temporary files. If the video goes through HLS and the client accepts WebVTT inside HLS (subtitle profile `{"Format":"vtt","Method":"Hls"}`, as in Emby Web), the tracks are served, as in Emby, with `DeliveryMethod=Hls` and no link: `TranscodingUrl` gets `SubtitleStreamIndexes` and `ManifestSubtitles=vtt`, `master.m3u8` lists the tracks in index order (`EXT-X-MEDIA:TYPE=SUBTITLES`), and `subtitles.m3u8` is a single WebVTT segment for the whole duration (Emby cuts 6-second pieces) with `X-TIMESTAMP-MAP`, which ties cue times to the video segment timestamps. The player turns such subtitles on, switches and turns them off without a new PlaybackInfo. At most two extractions run at once; the rest wait for a free slot until the client cancels the request; a job is limited to 2 minutes and 10 MiB of output and ends when the connection drops; an FFmpeg failure gives 404 and a `Subtitle unavailable` warning. Embedded image subtitles (PGS, DVD, DVB) are burned in, as Emby does: PlaybackInfo marks them `DeliveryMethod=Encode`, and a selected one turns the stream into an H.264 transcode with `SubtitleStreamIndex` and `SubtitleMethod=Encode` in `TranscodingUrl`; FFmpeg overlays the track on the video before scaling. Emby Web asks for a new PlaybackInfo when such a track is selected or turned off, so turning it off returns to Direct Stream or remux. The subtitle canvas is the video frame: a track drawn for a larger frame than the video is cut off at the bottom. Without FFmpeg in PATH, without an HLS profile that accepts H.264, and for a text track that cannot be extracted, the selected track is skipped: the video plays without subtitles (`DefaultSubtitleStreamIndex=-1`), and `Subtitle not deliverable, playing without it` is written to the log. Extracted subtitles are not cached: the file is read in full on each playback with them. If the client has not chosen a track itself, Couch chooses one based on the user's subtitle mode (mode descriptions taken from Emby Web): "Default" — tracks with the forced or default flag (forced first), "Smart" — a track in the preferred language if the audio language differs, "Only forced", "Hearing impaired" — tracks in the preferred language, SDH first, "Always" — tracks in the preferred language, "None". Languages are compared using the `Localization/Cultures` list (`ru` = `rus`), and preference order is respected; only tracks Couch can serve are chosen, and a text track is preferred to an image track that needs a transcode. The rules follow the descriptions, not captured reference responses. The selected audio track is reflected in DefaultAudioStreamIndex. If the client profile accepts it in the source file (the track is first or the profile does not set an `IsSecondaryAudio` condition), the file is served as is and the client switches the track; otherwise the file is repackaged to HLS with only the selected track. Rotated video (rotation in container metadata) is not served via remux: MPEG-TS does not store rotation, so the video is encoded to H.264 already rotated; the `VideoRotation` profile condition is checked. HDR video is tone-mapped as `-tonemap` says (above). The full set of Emby constraints is not covered yet.

The 30-second write timeout is renewed on every block: it limits a stalled write, not the duration of the whole transfer. The file is not loaded into memory in full. Cache validators come from the current size/mtime; the ETag is weak, not a content hash, so `If-Range` with an ETag results in a full response. Do not modify a file while it is being watched; catalog metadata is updated on restart or rescan.

When stopped at ≥90%, the video is marked played and the position is reset. A missing PositionTicks keeps the position; a negative one is rejected. For reports with a PlaySessionId, the last 64 playback starts per client session are kept: a repeated start does not increase the counter; progress/stop are accepted only for the latest unfinished playback. Within it, reports are applied in the order received, including seeking backward. Without a PlaySessionId, the previous received-order semantics remain, without deduplication. The window survives a restart; a repeat of a start already evicted from the window counts as new. A discarded report still gets 204, but a `Playback report ignored` warning is written to the log with the event type, reason and item ID; a stop without a position is noted with the message `Playback stopped without a position`. Image-based subtitles and full media compatibility are not implemented yet.

## Implemented contract

The API accepts routes with and without the `/emby/` prefix, case-insensitively. Query parameter values are kept unchanged.

| WebSocket | `/embywebsocket`: token sign-in, KeepAlive, ping/pong, UserDataChanged, UserConfigurationUpdated, LibraryChanged after a rescan, ServerShuttingDown on shutdown |
| Empty results for now | Upcoming, Missing (Couch does not know about missing episodes: it reads no episode lists), Live TV recordings |

Tokens are supported in headers, in the `X-Emby-Token`/`api_key` query, and in `Authorization: Emby …` and `MediaBrowser …`. Conflicting tokens are rejected. JSON sent by the client as `text/plain` with `reqformat=json` is supported. Unknown routes return 404. Errors, as in the reference Emby, are returned as `text/plain` with a readable message that Emby Web shows in a dialog.

The API field `Version=4.10.0.40` selects the matching branch of the client protocol. The Couch version is `0.1.0`, visible in `/healthz`, `X-Couch-Version` and the authenticated `/System/Info`. A matching protocol number does not mean full compatibility with Emby.

## OpenAPI contract

[api/openapi.yaml](api/openapi.yaml) is the Couch contract. It was derived once from the OpenAPI document that Emby Server 4.10.0.40 itself publishes (`GET /emby/openapi.json`; the source version and SHA-256 are recorded in `info.x-couch-derived-from`), and has been maintained by hand since. It is a derivative work of the Emby specification. The contract contains all 526 Emby operations and the Couch-only `GET /healthz`.

Differences from the source:

- only JSON is kept, the `application/xml` variants are removed;
- the reference server address is removed from `servers`;
- corrections confirmed by fixtures, the client or acceptance testing are marked `x-couch-source`. Currently these are the public pre-sign-in operations (Emby marks them as protected) and the JSON body of `POST /UserSettings/{id}/Partial`.

Emby schemas have no `required`, so only types and enums are checked, not field presence. Every success without a body is documented as `200`. The table above describes what is actually implemented; what is not implemented yet can be seen in the list of expected e2e failures.

## Storage and limitations

- Users: `-init` creates the first user as the administrator (`Policy.IsAdministrator`), so Emby Web shows "Manage Emby Server"; re-initialization is rejected. Administrator-only routes answer 403 to other users. Up to 100 users, each with their own settings, watch state, avatar and sessions.
  - On Emby Web's Users pages an administrator lists, creates, renames, hides, disables and deletes users, makes them administrators or not, sets or removes a password without the current one, and copies the policy or configuration from one user to others ("Copy from user" when creating one, "Copy Data to Users" in the list). A user cannot delete themself, and one enabled administrator always remains.
  - A new user has no password and cannot sign in until the administrator sets one. Disabling or deleting a user, or setting their password, signs them out everywhere. Users neither hidden nor disabled appear on the sign-in screen.
  - The policy stores the administrator role, disabled, hidden, and library access. The other policy settings are fixed to what Couch does, and a change to one is refused with its name, except content deletion and subtitle management, which the new-user page sets with the role, and channel access, which has no effect.
- Library access: on a user's Access tab, with "Enable access to all libraries" off, the administrator picks the libraries the user sees (#116). The policy stores library IDs; Emby Web names the libraries by their `Guid`, which Couch accepts and reports. The user then sees only those libraries everywhere: views, home rows (Latest, Continue Watching, Next Up), item lists, search, filter values, genres, studios, tags and people, item pages, series, seasons and episodes, images, PlaybackInfo, streams, HLS, subtitles, downloads, playback reports and marks. An item outside them answers 404, as a missing one does, and LibraryChanged events leave out changes in other libraries. A library added later stays hidden until the administrator enables it. An administrator always sees every library, so a limited policy for one is refused, as is an unknown library.
- Server dashboard (Manage Emby Server), for administrators only:
  - **Dashboard:** the server name and version, the port, sessions playing now with their item and position (from playback reports; a session counts as active for 10 minutes after its last request), alerts and recent activity.
  - **Activity:** sign-ins and failed sign-ins (with the client address), playback start and stop, user and library changes, library scans and a metadata refresh an administrator ran are stored in `couch.db`, the latest 1,000; the activity and alerts lists show them.
  - **Scheduled tasks:** "Scan media library" and "Refresh metadata" (changed `.nfo` files, items not yet found, missing images and, with `-metadata-refresh`, aged metadata), with their last run and result; both run on request. A running task cannot be stopped.
  - **Logs:** the log Couch writes to standard error also goes to `logs/couch.log` in `-data`, rotated at 10 MiB, with the four previous files kept (`couch-1.log` is the newest); the logs page lists and opens them. The log holds no tokens, passwords or request URLs.
  - **Devices:** each device a session signed in from; deleting one signs it out, except the device in use. Devices cannot be renamed.
  - **Settings:** only the server name can be changed (the "…" menu on the dashboard); it is stored in `couch.db` and replaces `-name`. Other settings are shown as Couch runs and a change to one is refused with its name; saving a page unchanged works.
  - **Features Couch does not have** (plugins, API keys, Emby Premiere, Live TV, conversions, release notes, codec settings) show empty pages. Restart and shut down are refused: Couch is run by its service manager or container runtime.
- Password: PBKDF2-HMAC-SHA256, 600,000 iterations, a random 16-byte salt. Only token hashes are kept in the state.
- Up to 64 sessions, 30-day lifetime; logout persists the revocation to disk. Sign-in is limited to 10 attempts per minute per address (IPv6: per /64 network), 100 attempts per minute per server and two concurrent password computations. `X-Forwarded-For` headers are ignored: behind a reverse proxy all clients share one address.
- State: SQLite database `data/couch.db` (`modernc.org/sqlite`, so the binary stays static), permissions 0600. Each change is one transaction that writes only the changed rows (a progress report updates one row), with the rollback journal and `synchronous=FULL`, so a commit is on disk before the response. Reads come from the state in memory, which a change replaces instead of modifying, so requests share it without copying; with 20,000 tracked items a change takes about 6 ms on one CPU and an item list does not slow down. Concurrent startup on the same directory is blocked. A corrupted database is not reset automatically.
- Request body size is up to 64 KiB; user settings, configuration and home screen sections up to 1 MiB together (at most 100 sections), 20,000 items with saved watch state.
- Sessions, settings and watch state survive a graceful restart and a `SIGKILL` in the middle of a write (checked by `make e2e`); the next start rolls back an interrupted transaction from `couch.db-journal` and deletes temporary files of interrupted avatar uploads. Every file the database refers to is synced before the commit, and a full disk fails writes with 500 without changing saved state ([VALIDATION](docs/VALIDATION.md)); a real power cut, NAS file systems and migration from Emby have not been verified.
- Backup: `couch -data DIR -backup NEW_DIR` writes a consistent copy while Couch runs or is stopped: `couch.db` through SQLite's `VACUUM INTO`, then the avatar files that copy references (`user-image-*`). A change saved during the copy waits for it (up to 5 seconds, then the request fails); the copy is loaded and checked before the command reports `Backup written.` In a container: `podman exec couch couch -data /data -backup /data/backup-2026-11-01`, then `podman cp couch:/data/backup-2026-11-01 .` and remove the directory from the volume. The copy contains password and token hashes: keep it as restricted as the directory itself. Restore: stop Couch, delete `couch.db`, `couch.db-journal` (if present) and `user-image-*` from the `-data` directory, copy the backup's files into it, start Couch. The state as of the copy comes back: the users and their passwords, sessions (ones logged out later become valid again until they expire), marks and positions, collections, playlists, stored metadata, and the media index with each file's date added, so the restored server starts without a full scan. Downloaded provider images (`metadata/`) are not copied; they are downloaded again after the restore. The `make e2e` check takes a backup while Couch runs and restores it after `SIGKILL`.
- Data upgrades: the database schema version is `PRAGMA user_version`; startup rejects a newer one without overwriting the database. Version 2 adds the `metadata` table, version 3 the administrator role, version 4 the rest of the stored policy, version 5 the libraries, version 6 the activity log and the server name, version 7 the identification an administrator chose, version 8 the collections, version 9 the playlists, version 10 the home screens arranged in Emby Web, and version 11 the media index; an older database is upgraded on the first start, and its existing user becomes the administrator. A `state.json` from builds before the database is not read: there was no release, so it is not migrated.
- WebSocket sends UserDataChanged after "played", "favorite" and progress are saved, to all active connections of that user. After `Users/{id}/Configuration` is saved (subtitle mode, languages, etc.), the user's connections receive UserConfigurationUpdated with the user as each of them sees it: Emby Web replaces the cached user with it, and the setting takes effect in other tabs and on other devices without a reload. `UserSettings` are not part of the user and do not send the event. On a graceful shutdown (SIGTERM, Ctrl+C) each connection receives `ServerShuttingDown` and a 1001 close frame, all in parallel; a client that has stopped reading delays shutdown by no more than a couple of seconds. Each connection may have 32 pending events; on overflow it is closed without delaying the API or other clients. There is no log/redelivery: after reconnecting, state must be re-read via the API.
- Logout closes all WebSocket connections of its session without affecting others. Token validity is checked before an event, on incoming frames and every 20 seconds on ping; stopping Couch closes open connections.
- Other server events, remote control, item editing, deleting media files and a custom frontend are not implemented.

## Verification

```sh
go -C src test -race ./...
go -C src vet ./...
go -C src build -o ../bin/couch ./cmd/couch
node scripts/check-emby-client.mjs
COUCH_CHECK_MEDIA=1 node scripts/check-emby-client.mjs
COUCH_WEB_DIR=../emby-webui COUCH_CHECK_MEDIA=1 node scripts/check-emby-client.mjs
```

The scenario requires Node.js with `fetch` and a global `WebSocket`. It creates a temporary user and directory, starts/restarts Couch on a free loopback port and checks the exchange of the original API modules. With `COUCH_WEB_DIR` the modules are read from the local UI; without it, access to Emby is required. Production Emby data is not modified; test processes are stopped and temporary state is deleted.

The `COUCH_CHECK_MEDIA=1` variant requires FFmpeg and FFprobe: it generates a synthetic video and checks the catalog/metadata, skipping a broken file, a stable ID, PlaybackInfo negotiation by the original API client, stream bytes, HEAD/Range/416/401, position persistence after a restart and playback completion. The source is checked by SHA-256. Without the variable, the empty-library scenario runs.

Another instance/binary can be specified via `EMBY_REFERENCE` and `COUCH_BINARY`. The check expects web version 4.10.0.40; a version change requires revisiting the contract. The report prints module SHA-256 hashes and routes without tokens. Application events and browser storage are replaced with minimal adapters. In the media scenario, the original ApiClient opens a WebSocket, receives UserDataChanged and reconnects after a restart; closing on logout is checked. The DOM, player and connection manager are not checked.

The same commands are in the `Makefile`: `make` (lint, test, build), `make lint` (golangci-lint v2 per `.golangci.yml`, including go vet and the gofmt/goimports check; installed separately), `make vet`, `make build-linux` (Linux amd64, `CGO_ENABLED=0`), `make release` (the same build as in the image, with its SHA-256, for [docs/INSTALL.md](docs/INSTALL.md)), `make check` (build and the Node scenario; environment variables are passed as above), `make e2e`, `make e2e-report`, `make clean`. `make lint` also checks the `e2e/` module with the same `.golangci.yml`.

CI ([ci.yml](.github/workflows/ci.yml)) runs on push to `main` and on every pull request. Stages run sequentially, each one only after the previous one succeeds:

1. Build: golangci-lint v2.14 for both modules, `make build build-linux`.
2. Tests: `make test` and `make e2e` in `golang:1.26-alpine3.24` with FFmpeg 8.1, as in the image, as a non-root user. The HLS tests also pass with FFmpeg 6.1 and 7.1 (Alpine 3.21, Debian 13).
3. Container: image build and `scripts/check-container.sh` on linux/amd64 and linux/arm64.

Build and tests run on Go 1.26, the version from `src/go.mod`; the image is built with the same Go line (`golang:1.26-alpine3.24` in the `Dockerfile`). The Node scenario (`make check`) does not run in CI.

### Contract E2E

```sh
make e2e
make e2e-report
```

`make e2e` builds Couch and generates a synthetic media library with FFmpeg: a movie with two audio tracks, an embedded and an external subtitle and a poster; a series with `Season 00`; audio and photos. It then starts instances on loopback and checks every operation in `api/openapi.yaml`:

- without a token, 401 is expected if the operation is protected;
- with a token, the documented success is expected: for operations with a JSON body, 200, `application/json` and schema conformance; for the rest, any 2xx.

GET and HEAD run in parallel on a shared instance; each mutation gets its own. Behavior checks in `e2e/behavior_test.go` cover scenarios for which the response shape is not enough: HLS, WebVTT, Next Up in Resume, persistence of a confirmed position after `SIGKILL` in the middle of playback reports, a 500 response without publishing the change when the data directory is not writable (do not run as root), a second user created by the administrator who signs in with separate watch state, survives `SIGKILL` and is deleted. Requires FFmpeg with libx264 and FFprobe. A run takes about 20 seconds.

The long-running load test runs separately: `cd e2e && COUCH_SOAK=10m go test -run TestSoak -timeout 30m ./...` (`COUCH_SOAK_WORKERS`, default 8; `COUCH_SOAK_RESCAN`, the interval between rescans, by default an eighth of the run). Each worker loops requesting the catalog, an item page, PlaybackInfo, the entire movie stream and a progress report; every fifth iteration it reconnects to WebSocket (alternately closing the connection with a close frame and dropping it), and every tenth iteration it requests embedded subtitles (FFmpeg). Workers 0 and 1 play the first remux-to-HLS segment every fourth iteration, worker 2 the first transcode segment, and they end the session via `ActiveEncodings/Delete`: together they occupy all FFmpeg slots. Throughout the load, the process is periodically sent `SIGHUP`, a rescan during playback. The test records RSS, the number of open files (`lsof`) and child processes (`pgrep`), and fails on request errors, leftover child processes, growth of open files by more than 2 (the test client's idle connections), changes to the set of files in the data directory (rotated server logs aside), and an RSS peak in the second half of the run more than 5% above the first half's: the stability criterion in [ROADMAP](docs/ROADMAP.md) M0 (#15), which takes `COUCH_SOAK=4h COUCH_SOAK_RESCAN=75s` on the large profile. Without `COUCH_SOAK` the test is skipped.

`e2e/known_failures.go` is a map of expected failures: `operationId` or check key → issue and reason. It works like `xfail(strict=True)`:

- a failing test in the map is marked as skipped with the reason;
- a passing test in the map fails the run: the entry must be removed;
- a failing test not in the map fails the run as a regression.

TDD cycle: remove the entry → see the failure → implement → the test turns green. `make e2e-report` builds an Allure report (Allure CLI 3) in `e2e/allure-report`. The test title is the operation `summary`; labels: epic (Contract or Behavior), feature (Emby service), story (`operationId`); requests and responses are attached to steps; expected failures have a link to the issue.

In a restricted environment, Go may need an accessible `GOCACHE`, and network tests may need permission for loopback connections. Results of the current run: [VALIDATION.md](docs/VALIDATION.md).
